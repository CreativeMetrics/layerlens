# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm install          # install deps (Node 18+ required)
npm run dev          # dev build with HMR (loads as unpacked extension)
npm run build        # tsc --noEmit + production build → dist/
npm run typecheck    # type-check only, no emit
```

There are no tests and no linter configured.

To load the extension: Chrome → `chrome://extensions` → Developer mode → Load unpacked → select `dist/`.

## Architecture

This is a Chrome MV3 extension built with Vite + [`@crxjs/vite-plugin`](https://crxjs.dev/). The plugin resolves entry points declared in `src/manifest.ts` and bundles them. The `@` alias maps to `src/`.

### Execution contexts

The extension runs code in three distinct JS worlds that cannot share variables:

| Context | Files | World |
|---|---|---|
| Service worker | `src/background/background.ts` | Extension |
| Content scripts | `src/content/*.content.ts` | Isolated (DOM access, no `window.*` page globals) |
| Injected scripts | `src/injected/*.inject.ts` | PAGE (full access to `window`, `dataLayer`, GTM internals) |

Content scripts bridge to injected scripts via `window.postMessage`. The injected scripts are loaded by content scripts using the crxjs `?script&module` import pattern (e.g. `import path from '@/injected/foo.inject.ts?script&module'`), which gives back the extension-scoped URL to pass to `document.createElement('script')`.

### Message protocol

Two typed message unions in `src/types/messages.ts`:
- `RuntimeMessage` — `chrome.runtime` / `chrome.tabs` messages (background ↔ content/popup). Uses a `code` key for most messages; a legacy `action` key for some older ones.
- `PageMessage` — `window.postMessage` messages (content ↔ injected page-world). Also uses `code` / `action` keys.

Helpers in `src/lib/messaging.ts` (`sendRuntime`, `sendToTab`, `onRuntimeMessage`) wrap the raw Chrome API with typed signatures and handle the async reply pattern.

### Key library modules

- **`src/lib/storage.ts`** — typed promise wrapper over `chrome.storage.local`. `StorageSchema` is the single source of truth for all persisted keys and their types.
- **`src/lib/gtm-selectors.ts`** — all CSS selectors that reach into the GTM web UI in one place. When Google reworks the UI, this is the only file to update. Also exports `pageType()` which detects TAGS / TRIGGERS / VARIABLES / CLIENTS.
- **`src/lib/gtm-angular.ts`** — guarded access to GTM's AngularJS internals (`window.angular`). Every call is wrapped in try/catch so a GTM UI change degrades a single feature rather than crashing the injected script.
- **`src/lib/filters-engine.ts`** — pure filtering logic (no DOM): builds type facets from rows, applies type + name + pause filters.
- **`src/lib/filters-schema.ts`** — `FiltersConfiguration` type + `normalize()` (coerce any input to valid config) + `validate()` (strict, for the Settings JSON editor).

    - **Container resource dump (best-effort)** — on export click, `popup.ts` `exportGtmInfo()` (async) re-fetches each `gtm.js` as text and runs `extractResourceJson()`: a string-aware balanced-brace scan (no eval/Function — security rule 4) that locates `"resource":{...}` and `JSON.parse`s it. `summarizeResource()` flattens `resource.macros`/`tags`/`predicates`/`rules` into arrays with an added `index` (position = the reference used by `rules`/`predicates`) and a `typeLabel`/`label` from `GTM_TYPE_LABELS` (maps `__v`→"Data Layer Variable", `__gaawe`→"GA4 Event", `__cl`/`__lcl`/`__evl`/`__sdl`/`__hl`/`__ytl`→trigger types, `_eq`→"equals", etc. — best-effort, unknown `function` codes pass through unchanged).     - **Macro reference resolution** (technique confirmed against `joangpega/gtm-spy` source) — compiled `vtp_*` params that are bound to a variable use the format `["macro", N]` (N = index into `macros`). `resolveValue()` recursively walks values/objects/arrays and replaces any `["macro", N]` with `{ macroRef: N, macroType: <typeLabel of macro N>, value: <resolved vtp_defaultValue ?? vtp_value ?? vtp_name of macro N, recursively resolved> }` (depth-capped at `MAX_RESOLVE_DEPTH = 6` to avoid cycles). `resolveParams()` applies this to every `vtp_*` key and returns a `resolved` companion object — added to every macro, tag, and predicate in `summarizeResource()`. This is what lets the export show e.g. the actual GA4 event name even when it's set via a variable rather than a literal.

Un service worker MV3 inattivo per ~30s viene terminato; il messaggio `DL_BG_PUSH` (es. il replay del carryover subito dopo una navigazione) è spesso ESATTAMENTE quello che lo risveglia — e in quell'istante la cache non ha ancora finito di caricarsi dallo storage, quindi il valore letto era ancora il default e il push veniva scartato anche se il capture era realmente attivo. Spiegava il pattern "funziona se il SW è già caldo, fallisce un click su due altrimenti". Fix: `dlBgCaptureEnabled` è ora `boolean | null` (`null` = "non ancora caricato in questa vita del SW"); il case `DL_BG_PUSH` controlla questo stato — se `null`, ritorna `dlBgCaptureReady.then(() => handleDlBgPush(msg, sender))` (una Promise tiene in vita il SW finché lo storage read non risolve, invece di correre contro di esso), altrimenti resta sincrono come prima (nessun overhead nel caso comune, SW già caldo).
          - **Export dell'ispettore dataLayer (`exportDataLayer()` in popup.ts) non includeva il carryover (2026-06-18)**: distinto dall'export GTM (`exportGtmInfo()`, pulsante "Esporta" vicino al badge container) — l'export dentro l'ispettore dataLayer usava SOLO `historyPages`/`currentPushes` (stato del popup, alimentato da `DATALAYER_PUSH` live), mai il log di background. Soffriva quindi della stessa race di sopra ma SENZA alcun backstop, perché non leggeva mai `tabDlLog`. Fix: `exportDataLayer()` ora è async, chiama `getBgDataLayer(tabId)` (`GET_DL_LOG`) e aggiunge alle pagine precedenti qualsiasi push presente in `bgLog` ma non già in `historyPages` (dedup per `url+JSON.stringify(push)`, stesso pattern di `exportGtmInfo`), taggando le entry aggiunte con `_page` (l'URL d'origine, dato che non appartengono a un `PageRecord` esistente). Additivo e retro-compatibile: se `dl_bg_capture` è spento, `bgLog` è vuoto e il comportamento è identico a prima.
          - **Limite noto, non risolto (architetturale)**: la vista LIVE nell'ispettore (lista push a schermo mentre si naviga) non può mostrare un push che avviene dopo che il popup si è chiuso — e il popup di Chrome si chiude automaticamente alla perdita di focus, incluso il click su un link della pagina che porta alla navigazione. L'export è corretto (legge il log di background, persistente e indipendente dal popup), ma la UI live no — per risolverlo servirebbe un componente persistente (es. side panel) invece del popup standard, cambio di scope non perseguito.
          - **Fix `_ts` mancante sui push iniziali (per `consentGrantedAt`, 2026-06-18)**: `ensurePushWrapped()` inizializzava `__llTs` a `[]` al primo aggancio, lasciando senza timestamp i push già presenti nell'array prima di quel momento (init GTM, consent default/update — tipicamente i primi ~16 push, spesso prima che il nostro script faccia in tempo ad agganciarsi). `computeConsentGrantedAt()` (popup.ts) scarta silenziosamente ogni push `consent`/`update` senza `_ts` numerico, quindi `capture.consentGrantedAt` restava quasi sempre `null` anche quando il consenso era stato dato, proprio perché il comando `update` è spesso tra questi primi push non timbrati. Backfill: al primo attach, `__llTs` viene inizializzato a `new Array(arr.length).fill(Date.now())` invece di `[]` — i push pre-esistenti vengono timbrati con l'istante di aggancio (la miglior approssimazione disponibile), invece di restare senza `_ts` per sempre.
          - **Fix inversione `consentTimeline.default`/`afterChoice` (2026-06-18)**: `buildConsentTimeline()` eseguiva PRIMA il rilevamento basato su rete (primo `gcs` visto = `default`, valore diverso successivo = `afterChoice`) e SOLO DOPO quello basato su dataLayer (comando esplicito `'default'`/`'update'`) — ma quest'ultimo veniva scritto solo se `!defaultState`/`!afterChoiceState`. Su siti con Consent Mode "rigoroso" (nessun tag spara nessuna request finché il consenso non è concesso), il PRIMO `gcs` mai visto in rete è già lo stato POST-scelta — il rilevamento di rete lo marcava (erroneamente) come `default`, e il valore corretto dal dataLayer veniva poi scartato dal guard `!defaultState`. Risolto invertendo l'ordine: il pass dataLayer (autoritativo, usa il nome esplicito del comando) ora gira PRIMA; il pass di rete si limita a riempire ciò che il dataLayer non ha già stabilito. Applicato lo stesso ordinamento cronologico per `ts` (già usato in `buildConsentTimeline`) anche a `computeConsentGrantedAt()`, per consistenza.
        2. **`chrome.debugger` per-request initiator capture** — `attachDebugger()` (per il campo `network[].initiator` dell'export) viene chiamato da `webNavigation.onBeforeNavigate` **solo se** `dl_bg_capture === 1` in storage: prima girava sempre, su ogni navigazione di ogni tab, e faceva apparire il banner di Chrome "LayerLens ha iniziato il debug di questo browser" ad ogni caricamento pagina anche senza alcun bisogno di export. `chrome.storage.onChanged` su `dl_bg_capture` attacca/stacca il debugger sulle tab già aperte immediatamente, senza aspettare la prossima navigazione.

### CSP note

On install the background strips `content-security-policy` **and** `x-frame-options` headers globally via `declarativeNetRequest` to allow injected GTM and preview to run on CSP-strict sites. This is a known intentional trade-off flagged for future scoping.

`x-frame-options` must be stripped together with CSP: per spec, when a response carries both CSP `frame-ancestors` and `X-Frame-Options`, the browser ignores XFO and obeys `frame-ancestors`. Stripping CSP alone removes the `frame-ancestors` that was permitting an iframe, which newly exposes an `X-Frame-Options: deny` and breaks iframes that loaded fine before (confirmed on `gestione-eventi.atlantiscompany.it`: disabling the extension made the "Refused to display … X-Frame-Options to deny" error disappear). Keep the two removals paired.
